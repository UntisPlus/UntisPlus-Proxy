# Account safety, runtime and delivery audit

This follow-up reviews the implementation after `663f3d4`. It uses temporary
SQLite databases and fake upstream servers. No teacher account writes are part
of the checks.

## Account boundaries

- A verified login binds a username to one school. The current schema uses
  globally unique usernames: the same username at a second school is rejected,
  rather than merging identities or replacing another school's credentials.
- Replay secrets are read only for their owning school. Upstream key login
  receives the submitted current code, never a previously stored replay key.
  Failed or foreign-school enrollment cannot overwrite the owner's credentials.
- Upstream profile updates cannot grant server administrator rights. Existing
  explicit grants remain; deleted accounts do not inherit their former grant.
- App sessions store the user's database ID as well as username. Deleting and
  recreating a username cannot revive its old sessions. Account deletion clears
  saved sessions, credentials, permission overrides, private records and owned
  subscriptions/calendar links. Administrative audit records remain.
- Session reads return independent copies. Creation and revocation serialize
  durable writes, and the manager has a shutdown method for maintenance.
- REST pooled timetable reads check the viewer's permission before using a
  donor. Reconstruction checks the effective capability, including server gates
  and per-user denials.
- Invalid TOTP secrets produce no code instead of the predictable `000000`.

### Upgrade and rollback

The schema adds `secrets.school` and `proxy_sessions.user_id`. On startup,
previously unrecorded school ownership is backfilled from the configured default
or recorded user school. Back up the database first. Existing real-account
sessions without an account ID are discarded: users must log in once after this
upgrade. New sessions survive subsequent restarts. Accounts are retained.

Old binaries do not enforce these session and school boundaries. Do not expose
a rollback publicly until the relevant restrictions are restored. A rollback
requires the matching pre-upgrade database backup if old semantics are needed;
stop the service before restoring it. Never overwrite a running database.

## Permission lookup optimization

Permission decisions and group previews use one SQLite read snapshot. Group
rules are loaded in batches, and feature switches use indexed scope ranges.
Memoization is confined to one request/transaction: a later request sees committed
permission revocations immediately. Read-only transactions use deferred SQLite
BEGIN, so they do not take the poller's immediate write lock.

The benchmark fixture now selects an actual account in the requested school;
the former even-numbered class tested an empty result. With 5,000 synthetic
accounts, the same corrected fixture on the previous commit and this revision
measured permission resolution at 57,592 versus 22,569 allocated bytes, and 685
versus 504 allocations per call (about 61% fewer bytes and 26% fewer allocations).
Timings varied under concurrent verification load; these figures are not a
production latency guarantee.

## Runtime and release pipeline

The runtime image uses one administrative binary with `untis-seed` and
`untis-perm` aliases. Standalone Go commands remain available. Existing CLI names,
flags and help remain supported. The measured local amd64 image shrank from
54,012,241 to 36,717,569 bytes, about 32%, on the final beta image.
The Docker build cross-compiles natively and keeps module/SQLite layers separate
from application and version changes. The build context admits only required
source and embedded HTML; credentials and operational documents are excluded.

The release workflow checks the exact compiled version on both amd64 and arm64
before publication, including default startup, non-root/read-only restrictions,
CLI aliases and an offline backup/restore. Publication includes provenance and
an SBOM. GitHub release creation has a separate narrowly scoped write permission.
Prereleases do not replace `latest`.

`scripts/release.sh` submits one explicit release tag after local checks. It no
longer pushes native-only Docker images over `latest`, pushes unrelated tags,
or bypasses the tested multi-platform publishing workflow. `PUSH=0` remains the
local-only gate. Publication success must be checked in GitHub Actions.

## Verification and remaining acceptance

Regression coverage includes foreign-school credential writes/reads, server
administrator preservation without resurrection, stale-session rejection,
permitted versus denied pooled reads, session copies, and multi-school pool
isolation. Existing functional, UI, race and offline-container checks remain the
release gates; record their final result in the deployment report.

Production acceptance still requires representative teacher/student/guardian
read-only checks, browser/mobile visual checks, sustained load and an operational
rollback exercise. Automated coverage does not establish every possible edge
case or upstream response variant.

Useful next API additions are a versioned OpenAPI contract, a read-only
"why is this request denied?" explanation using the existing permission resolver,
and explicit linked-child selection across the remaining guardian workflows.
These remain proposals, not newly exposed endpoints.
